**Option A — A guarded production runner, modelled on the first-manager tool.**

## Route A — BUILT, PENDING REVIEW AND HUNTER'S OPEN-1 CHOICE

**Status:** built locally on branch `bb/build-route-a-guarded-production-sql-runner-loca-thr_3d8aqs6pdj`; **not reviewed, not run against any hosted database, not approved.** It does not decide OPEN-1. If Hunter picks Route B or C it can sit unused: nothing else depends on it, and no file here is edited by it.

**What exists:** `pipeline/src/prod-sql.ts` (action table, planner, executor), `prod-sql-split.ts` (offline statement splitter and transaction-shape detector), `prod-sql-runner.ts` (command line, `npm run prod-sql` in `pipeline/`), the new `prod-sql.*` events and seven `prod_sql_*` refusal ids in `scripts/run-with-secrets.mjs`, tests `prod-sql.test.ts` (offline) and `prod-sql-a3.test.ts` (real PostgreSQL 16, loopback), and `scripts/verify-prod-sql-runner-contract.mjs` (wired into CI and `.github/ci/repository-safety.sh`).

**How it behaves (each point has a test):**
- One **action** per approved file or stage, 20 in all: the four July migrations (A2), `snapshot` (A3), `m1`, `m1b`, `m1c`, three L1 stages (`l1-shape`, `l1-counts`, `l1-sweep`), six `retire-app-credentials.sql` stages, and `backout-m1c`, `backout-m1b`, `backout-m1`. Each pins the file's SHA-256 (a stage also pins its own statements) and refuses on any mismatch; migrations must also agree with `migration-checksums.sha256`.
- **Production only:** `--target=production` has no default; the address must be the one recorded production project, on port 5432. Staging, local and anything else are refused.
- **The address** comes only through the hidden prompt of `scripts/run-with-secrets.mjs` (`--secret PRODUCTION_DB_URL`); a value already in the environment is refused.
- **One typed phrase per action** (`--confirm="RUN TNBS PRODUCTION SQL <ACTION>"`); **plan-only** unless `--execute`.
- **Transactions:** a file with no top-level `begin`/`commit` (M1, the migrations, `retire-nologin`) is wrapped in one transaction; a file with its own (M1b, M1c, the backouts, `l1-sweep`, `retire-revoke`) is run as written and never wrapped again; any other shape is refused. Read-only actions run in `begin read only` and are rolled back. Each write transaction also sets a 10-second lock wait so it cannot queue behind the live app indefinitely.
- **Output:** fixed events only (counts, enumerated words, the pinned file hash). Row-returning stages print numbers only: `snapshot` prints a SHA-256 of each result so before/after can be compared without printing rows; count stages print pinned column names with numbers.
- **L1 shape gate (doc 17 B13 stage 1):** `l1-shape` does not just hash the two schema listings. It judges them against the L1 file's own shape check and prints one `prod-sql.shape` event of fixed yes/no checks (`table_users`, `table_sessions`, `table_refresh_tokens`, `table_one_time_tokens`, `table_flow_state`, the six `users_<token column>` checks, `results_read`, `no_unreviewed_auth_tables`) plus two counts (auth tables found, auth tables not on the reviewed list). It never prints a table or column name from the database. Any failed check **stops the run** (`prod_sql_l1_shape_not_ok`). `l1-sweep` runs the same two selects first, inside its own transaction and before its first delete, and refuses on the same terms, so a sweep can never proceed on a shape the gate would refuse. The reviewed list is the 27-table classification in `supabase/rollout/auth-table-classification.json` (see the auth table inventory section below); an auth table that is **not listed** counts as unreviewed until a reviewed change classifies it (the runner never deletes an unlisted table). A table listed as `credential-bearing: STOP` is reviewed but must be **empty**: that is judged separately, under a lock, inside the sweep's own transaction (see "STOP tables: stop unless empty" below). `l1-shape` only reports the STOP-table counts as information.
- **Stage coverage:** the stages of `L1-close-legacy-auth.sql` and `retire-app-credentials.sql` must tile their file exactly, from statement 1 through the last statement, with no gap and no overlap; a statement that no stage would run is refused at plan time, and `scripts/verify-prod-sql-runner-contract.mjs` recomputes every stage digest itself.
- **COMMIT rules (CR17):** a failed COMMIT is reported `unknown`, never retried, never rolled back; a COMMIT that returns the ROLLBACK tag is a definite failure.
- **Irreversible step: ending connections (`retire-terminate`).** This action runs `pg_terminate_backend` on every connection of the application role (doc 17 BO2 step 3). Ended connections **cannot be undone**: the rollback does not restore a connection that has already been ended, and the runner's `rolled_back`, `rollback_not_confirmed` and `unknown` results describe SQL changes only. "A failed file rolls back as a unit" (Option A above) is therefore true of SQL changes and **not** of this step. The runner warns in three places, all fixed text that the wrapper allow-lists (`prod-sql.warning`: a fixed id plus a fixed sentence, never database text):
  1. **With the plan, before anything connects**, for plan-only and `--execute` alike: `connections_end_cannot_be_undone`. The operator reads it before typing the owner's go.
  2. **After any run of that action that ends in an error** (`rolled_back`, `rollback_not_confirmed` or `unknown`): `rollback_does_not_restore_connections`, printed right after the result line.
  3. **In this section.** Doc 17 BO2 needs the same wording; the manager has the recommended text, and doc 17 is not edited on this branch.

  What the operator does after an error in this step: **STOP**, do not retry, and read the real connection count with the `retire-backends` action (a read-only count of the application role's connections). Keep the doc 17 BO2 rule: poll once a second, continue only after it reads 0 three times in a row, and if it has not read 0 three times in a row within 60 seconds, stop and escalate. The runner does not poll for the operator and never tries to reconnect ended sessions. `L1` has **no** termination statement: its irreversible effect is that the closed sign-in credentials have no backout (doc 17 B13), which is already recorded there. No extra typed phrase was added for this step beyond its own per-action phrase and the owner's go; if Hunter wants a second, distinct phrase for it, that is a separate decision. `scripts/verify-prod-sql-runner-contract.mjs` derives the set of irreversible actions from the pinned statements themselves (every action whose statements call `pg_terminate_backend`), so a new or changed action cannot skip the warning, and it fails if the warning, its wrapper allow-list entry or this paragraph is removed.

### STOP tables: stop unless empty (central item 28, option 1) — BUILT LOCALLY, PENDING INDEPENDENT REVIEW

**Status (2026-11-01 UTC):** built and tested on local throwaway PostgreSQL 16 only. Nothing was run against any hosted database, and no production read or execution was made. The independent review is still to come.

**What it does.** The thirteen `credential-bearing: STOP` tables are no longer an automatic refusal. Instead:
1. `l1-sweep` (stages 3 and 6) runs, inside its own transaction and **before its first delete or update**: (a) `set transaction isolation level read committed` (so the count after the lock sees a fresh snapshot even on a server whose default is repeatable read); (b) the existing 10 second lock timeout; (c) the existing two shape selects (an unlisted table still stops here, before any lock or count); (d) a catalogue lookup of which of the 13 tables exist in schema `auth`; (e) **one** `LOCK TABLE ... IN SHARE ROW EXCLUSIVE MODE` statement for every one that exists, in sorted order; (f) one `select count(*)` per existing table. Only counts are read; no column or row of these tables is ever selected. After L1's own statements and **before COMMIT**, the sweep (g) sends `SET CONSTRAINTS ALL IMMEDIATE`, then repeats (d) and (f): a second catalogue lookup and a second `select count(*)` for every table that exists then. `SET CONSTRAINTS ALL IMMEDIATE` makes PostgreSQL fire, right now and inside the rollback window, every deferred constraint trigger and every deferred constraint check that L1's statements queued (PostgreSQL documents that a constraint switched to immediate is checked at once, and that events queued while it runs fire at the end of that statement), so a STOP row such a trigger inserts is visible to the re-count, and nothing deferred is left to fire inside COMMIT. No statement runs between the re-count and COMMIT, so nothing new can be queued there. If any table is not exactly 0 (a trigger or cascade of the sweep's own transaction wrote a STOP table; a table lock cannot stop a transaction's own writes), it stops with the same fixed refusal `prod_sql_l1_stop_table_populated`, rolls back everything, and commits nothing. If a deferred check itself fails at that point (for example a deferred foreign key, 23503), the statement errors, nothing is committed, the run rolls back and prints `server_or_driver_error` with that SQLSTATE and result `rolled_back`; it is not relabelled as a refusal. The re-count prints no second event.
2. If every count is exactly 0 the sweep goes on exactly as before (L1's own statements are unchanged). If any table has a row, or a count cannot be read (it is treated as populated), the run stops with the fixed refusal `prod_sql_l1_stop_table_populated`, the transaction is rolled back, **nothing is cleared**, the STOP rows and all L1 data are left as they were, and the locks are released by the rollback.
3. A STOP table that the schema does not have (a different Auth release) is reported as `absent`, is not locked, and holds no rows.
4. `l1-shape` (read-only) prints the same event as information, with `locked: false` and no lock; it does not refuse on a populated table (the sweep does), and still refuses on an unlisted table. The event is printed only when the read-only run reaches that point, before the shape verdict.

**The event (`prod-sql.stop_tables`).** Fixed metadata only: `action`, the classification word `credential-bearing: STOP`, `locked`, a `tables` object (table name to its row count, or `absent`), `tables_present`, `tables_populated`, `passed`. **Table names may appear** because they come from the pinned classification file (a repository file whose SHA-256 is pinned), never from the database: the database answer is only compared with that list and never copied. A count is a number. The wrapper (`scripts/run-with-secrets.mjs`) allows the event only when every `tables` key is one of the 13 STOP names of the pinned classification (its `PROD_SQL_STOP_TABLES` copy; a test and the contract script compare it with the file, and a valid-looking name that is not pinned, or a pinned name that is not a STOP table, is withheld and counted as a field) and the value is a number or `absent`; anything else is withheld. The refusal ids are `prod_sql_l1_stop_table_populated` and `prod_sql_l1_stop_table_lock_failed` (both on the wrapper's allow-list; a test keeps the two lists equal). The runner does not repeat the list of 13: `stopTablesOf()` reads it from the classification file, and the contract script fails if any STOP table name is hard-coded in `prod-sql.ts`. The wrapper's output allow-list holds a copy of the 13 names (it cannot read TypeScript or trust the database), kept equal to the file by a test and the contract script.

**Why `SHARE ROW EXCLUSIVE` mode, and what it blocks.** It conflicts with `ROW EXCLUSIVE` (what INSERT, UPDATE, DELETE and COPY take) and with every stronger mode (TRUNCATE, DROP and ALTER take `ACCESS EXCLUSIVE`). Once the lock is granted no other session can add or change a row in these tables until the sweep ends. The lock is granted only after every transaction that already holds `ROW EXCLUSIVE` there (an insert that has not committed yet) has ended, so such a row is either committed and **counted**, or rolled back and absent. It does **not** block plain `SELECT`, `SELECT ... FOR UPDATE/SHARE` or foreign-key checks that only read, so reads and sign-in lookups keep working. **Why not plain `SHARE`:** `SHARE` is compatible with `SHARE`, so two sweeps could both be granted all 13 locks and pass every count; L1's own `delete from auth.flow_state` cascades into `saml_relay_states` (a captured foreign key with `ON DELETE CASCADE`), which needs `ROW EXCLUSIVE` there, and the other sweep's `SHARE` blocks it, so each waits for the other and PostgreSQL ends one with 40P01 (the independent review reproduced this). `SHARE ROW EXCLUSIVE` conflicts with itself, so a second sweep waits at its `LOCK` statement (it holds no L1 row locks yet) until the first ends, or refuses with `prod_sql_l1_stop_table_lock_failed` after the 10 second `lock_timeout`; it never deadlocks with the first. The sweep's own cascade into `saml_relay_states` is allowed (the table was counted empty, nothing else can write it, so the cascade deletes nothing and the re-count before COMMIT confirms it is still empty). It does **not** block writes to any other table, it cannot block the sweep transaction's **own** writes (hence `SET CONSTRAINTS ALL IMMEDIATE` and the re-count before COMMIT), and it protects nothing after the sweep ends: "empty" is a fact about the moment of COMMIT. The Supabase Auth service writing to one of these tables (for example enrolling a second factor, registering an OAuth client or a passkey) waits until the sweep ends, bounded by its own timeouts; it is not failed, and the wait is the length of one sweep. Whether anything on the hosted project writes to them during the window is **not verified**; the O2 step (provider and sign-up closure) is what keeps those features unused, and a populated table found afterwards is a reason to stop, not a state this check can prevent.

**Residual limits (not closed).** (1) A STOP table that does not exist when the catalogue lookup runs is not locked. If something creates and fills it during the sweep, the re-count before COMMIT repeats the lookup and will see it, but a row written by another session after that re-count cannot be excluded for a table that was never locked; no schema-wide DDL lock is taken, and concurrent creation of a missing table was not tested. (2) The re-count refuses on a trigger or cascade inside the sweep, including deferred constraint triggers (flushed by `SET CONSTRAINTS ALL IMMEDIATE`); it is tested with synthetic triggers only. A trigger that is not a constraint trigger cannot be deferred in PostgreSQL, so none can fire after the flush. Whether the hosted Auth schema has such a trigger is **not verified**, and PostgreSQL 16 locally does not prove hosted triggers, roles or the Auth release.

**What a failure to lock looks like.** If a lock cannot be granted within the 10 second `lock_timeout` (SQLSTATE 55P03), or PostgreSQL ends the wait as a deadlock (40P01), or a name turns out not to be a lockable object (42809), the run prints the fixed refusal `prod_sql_l1_stop_table_lock_failed`, rolls back, and has changed nothing (it fails before any count, delete or update). Any other lock error (for example a missing privilege, 42501) is not relabelled: it is reported as `server_or_driver_error` with its SQLSTATE and rolled back. The role the hosted runner logs in as may lack the privilege to lock some `auth` tables: **not verified**, and it would show as 42501, never as a partial sweep.

**Deadlock risk with L1's own statements.** Two sweeps cannot deadlock each other: `SHARE ROW EXCLUSIVE` conflicts with itself and the locks are requested in one sorted statement before any L1 statement, so the second sweep waits (or refuses after the lock timeout) and a real-PostgreSQL test with two concurrent sweeps shows one commits and the other waits for it with no 40P01. (An earlier version of this section said sorted locks prevented that; with plain `SHARE` they did not, see above.) A deadlock with a third transaction is still possible, and it does **not** need a STOP write: any transaction that holds a row lock on an L1 table and then waits for something we hold (a STOP table lock, or a row lock on a non-STOP table such as `users` or `sessions`) while our statement waits for its row lock closes the cycle (the independent review reproduced one with writes to non-STOP tables only: it updated `users`, the sweep deleted `sessions`, it then updated that `sessions` row and waited, and the sweep's later update of `users` waited for it). PostgreSQL ends one side after `deadlock_timeout` (1 second by default): either that transaction fails (the sweep goes on) or the sweep fails with 40P01 (reported as `server_or_driver_error`, rolled back, nothing changed; re-run). Both outcomes were reproduced locally (the independent review forced the sweep to be the victim and verified the rollback restored every L1 row).
